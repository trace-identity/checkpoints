# Trace 게시분 (checkpoints)

Trace 는 기록을 작성한 순간에 고정해 나중에 고칠 수 없게 하는 서비스입니다.
이 저장소에는 Trace 가 하루에 한 번, 그 날까지의 기록을 요약한 값 하나를 올립니다.
올라간 뒤에는 Trace 운영자도 기록을 바꾸면 이 값과 맞지 않게 됩니다.

Trace 서버를 믿지 않고도, 공유받은 기록이 여기 게시된 값과 맞는지 누구나 확인할 수 있습니다.

## 여기 올라오는 것

| 파일 | 내용 |
|---|---|
| `days/YYYY/YYYY-MM-DD.txt` | 그 날(한국 시간)의 게시 파일. 날짜, 그 날의 요약값(root), 바로 앞 날의 게시값(prev) |
| `days/YYYY/YYYY-MM-DD.txt.ots` | 위 파일의 [OpenTimestamps](https://opentimestamps.org) 시각 증명. 처음에는 "대기" 상태로 올라오고, 비트코인 블록에 들어간 뒤(보통 다음 날) 확정본으로 한 번 바뀝니다 |
| `verify.mjs` | 검증 스크립트(Node.js, 추가 패키지 없음) |
| `check.mjs`, `.github/workflows/check.yml` | 이 저장소의 파일이 온전한지 매일 살피는 감시 |
| `vectors.json` | 계산식의 기준값 |

날짜 파일은 한 번 올리면 바꾸지 않습니다. 기록이 없는 날도 파일을 올립니다.

**올라오지 않는 것:** 기록 내용, 이용자를 알 수 있는 값, 기록 하나하나의 지문, 하루 기록 건수.

## 확인하는 방법

공유받은 Trace 검증 화면의 "외부 게시" 아래 "검증 자료"를 복사해 파일로 저장합니다(예: `proof.json`).

```
node verify.mjs proof.json
```

스크립트는 Trace 서버에 접속하지 않습니다. 게시 파일은 이 저장소에서 읽습니다
(`--repo-dir .` 을 붙이면 내려받은 사본에서 읽습니다). 하는 일은 다음과 같고, 손으로도 할 수 있습니다.

1. 문장의 sha256 이 검증 자료의 `content_hash` 와 같은지 본다.
2. 정규 형식 2번대로 잎을 계산한다. 작성 시각과 입력 방식도 여기에 들어간다.
3. `path` 의 형제값을 순서대로 합쳐 값 하나를 얻는다.
4. `days/연도/날짜.txt` 의 `root` 가 그 값과 같은지 본다.
5. 그 파일의 sha256 이 다음 날 파일의 `prev` 와 같은지 본다.
6. 그 파일이 그 무렵에 실제로 있었는지 시각 증명으로 본다(아래).

게시분 날짜가 작성일보다 뒤인 기록이 있습니다(외부 게시를 시작하기 전에 쓴 기록, 자정 직전에 쓴 기록).
그런 기록에서 게시된 값으로 확인되는 것은 게시분 날짜 이후 바뀌지 않았다는 것뿐입니다.

### 시각 증명 확인

이 저장소는 Trace 가 관리합니다. 저장소만으로는 파일을 나중에 바꿔 올리지 않았다고 말할 수 없습니다.
`.ots` 파일이 이를 보완합니다: 날짜 파일이 어느 비트코인 블록 이전에 있었는지를 Trace 와 무관하게 보여 줍니다.

- [opentimestamps.org](https://opentimestamps.org) 에 `.txt` 와 `.txt.ots` 를 함께 올린다. 또는
- 비트코인 노드가 있으면 `ots verify days/2026/2026-11-23.txt.ots`
- 노드 없이: `ots --no-bitcoin verify …` 가 알려 주는 블록 번호와 merkleroot 를 블록 탐색기에서 대조한다.

표시되는 블록 날짜가 게시분 날짜와 가까운지(보통 하루 이내) 확인하세요. 블록 날짜가 훨씬 뒤라면 그 파일은
그때까지 바뀔 수 있었다는 뜻입니다. 게시 직후 몇 시간은 아직 블록에 들어가지 않아 "대기 중"으로 나옵니다.

## 정규 형식

계산에 쓰는 바이트를 한 가지로 정해 둔 것입니다. Trace 앱과 `verify.mjs` 가 같은 문장을 따릅니다.

```
1. 문장 지문(content_hash) = sha256(문장의 UTF-8 바이트). 소문자 hex 64자.
2. 잎 = sha256( 0x00 한 바이트 ‖ 아래 일곱 줄의 UTF-8 바이트 ).
   줄 사이는 LF(0x0A) 하나이고 마지막 줄 뒤에는 줄바꿈이 없다.
     trace-leaf/v1
     salt          소문자 hex 64자(무작위 32바이트)
     entry_hash    소문자 hex 64자
     content_hash  소문자 hex 64자
     created_at    UTC, YYYY-MM-DDTHH:MM:SS.ffffffZ (마이크로초 6자리)
     input_method  typed, voice, pasted, ai_chat, ai_assisted, bundle 중 하나
     seq           앞에 0 을 붙이지 않은 십진수
3. 노드 = sha256( 0x01 한 바이트 ‖ 왼쪽 32바이트 ‖ 오른쪽 32바이트 ).
4. 하루의 요약값(root): 그 날의 잎을 바이트 오름차순으로 늘어놓고 앞에서부터 둘씩 짝지어 노드를 만든다.
   짝이 없는 마지막 하나는 그대로 윗단으로 올린다. 하나가 남을 때까지 되풀이한다.
   잎이 없는 날의 요약값은 sha256(빈 입력) = e3b0c442…b855 이다.
5. 포함 증명(path)은 잎에서 요약값까지 가는 길의 형제값 목록이다. 각 단계에서 side 가 "L" 이면
   sha256(0x01 ‖ 형제 ‖ 현재값), "R" 이면 sha256(0x01 ‖ 현재값 ‖ 형제)를 계산한다.
6. 날짜 파일(days/YYYY/YYYY-MM-DD.txt)은 아래 네 줄의 UTF-8 바이트다.
   모든 줄은 LF(0x0A) 하나로 끝나고 마지막 줄도 LF 로 끝난다. BOM 과 CR 은 없다. hex 는 소문자다.
     trace-day/v1
     date:YYYY-MM-DD      한국 시간 기준 날짜
     root:<소문자 hex 64자>
     prev:<소문자 hex 64자> 바로 앞 날짜 파일의 sha256. 첫 파일은 0 을 64개 쓴다
7. 그 날의 게시값 = sha256(날짜 파일의 바이트 전체). 다음 날 파일의 prev 가 이 값이다.
```

salt 는 기록마다 따로 뽑는 무작위 값입니다. 이용자가 탈퇴하면 그 사람의 기록, 지문, salt 가 함께 지워집니다.
여기 남는 요약값만으로는 누구의 어떤 기록이 들어 있었는지 알 수 없습니다.

기준값으로 계산식을 확인하려면: `node verify.mjs --self-test`

## 이 확인으로 알 수 없는 것

- 기록을 쓴 때부터 다음 날 새벽 게시분이 올라가고 비트코인 블록에 들어갈 때까지(보통 하루 남짓)는 확인할 수 없습니다.
- 밖에서 확인되는 시각은 "게시분 날짜 이전에 이 값으로 있었다"까지입니다. 분 단위 작성 시각과 입력 방식은
  Trace 서버가 저장할 때 적은 값이며, 게시된 뒤에 바뀌지 않았다는 것만 확인됩니다.
- 기록 내용이 사실인지, 표시된 이름이 실제 본인인지, 사람이 썼는지는 확인하지 않습니다.
- 외부 게시를 시작하기 전에 쓴 기록은 게시를 시작한 날부터만 확인됩니다.
- 기록이나 그 검증 자료가 지워지면 그 기록이 있었다는 것을 이 방법으로 보일 수 없습니다.
  기록을 쓴 사람은 Trace 의 내보내기로 자신의 검증 자료를 받아 둘 수 있습니다(`node verify.mjs 내보내기파일.json`).
- 탈퇴한 사람의 기록은 검증 자료가 함께 지워져 더는 확인할 수 없습니다.
- 묶음의 설명과 서명 문구는 확인 범위 밖입니다. 결과물 이름, 파일 지문, 포함 기록은 묶음을 고정한 기록의 원문으로 확인됩니다.
- 기록의 일부를 가려서 공유하는 기능은 아직 없습니다. 그런 기능이 생기면, 가린 기록은 문장에서 출발하는 확인을 할 수 없습니다.

## 운영 메모

- 커밋은 Trace 서버가 하루 한 번(한국 시간 새벽 2시대) 자동으로 올립니다. 작성자는 `Trace Identity <noreply@trace-identity.com>`.
- `main` 브랜치는 강제 푸시와 삭제가 막혀 있습니다. 이력을 다시 쓰지 않습니다.
- `.github/workflows/check.yml` 이 매일 한국 시간 04:30 과 푸시 때마다 `check.mjs` 를 돌립니다. 비밀값을 쓰지 않습니다.
  어제 파일이 없거나, 파일이 이어지지 않거나, 시각 증명이 7일 넘게 확정되지 않으면 실패합니다.
- **공개 저장소의 예약 워크플로는 저장소에 60일간 활동이 없으면 GitHub 이 자동으로 끕니다.**
  게시가 60일 넘게 멈추면 감시도 멈춥니다. 다시 시작할 때 Actions 탭에서 워크플로를 켜야 합니다.
- 시각 증명이 14일 넘게 대기 상태로 남으면 자동 갱신 대상에서 벗어납니다. 그때는 저장소를 내려받아
  `ots upgrade days/YYYY/YYYY-MM-DD.txt.ots` 로 갱신한 파일을 직접 올립니다.
